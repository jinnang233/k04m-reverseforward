# 反向转发控制路径安全审查（2026-10-08）

本轮继续检查客户端、服务端中继和反向转发的控制消息、权限与资源边界，并检查文档站依赖。确认的问题和代码修复位于本仓库 `ForwardingManager`。这是针对性的人工检查与回归验证，不是完整安全认证。

## 修复的问题

### 待处理邀请无容量限制（拒绝服务）

远端发送不同 invitation ID 时，原实现会不断加入 `invitations`，并为每条打印提示。两分钟到期并不能限定这一期间的内存与提示数量，单个玩家也可以独占待处理状态。

修复为最多 64 个待处理邀请、每玩家最多 4 个。按玩家名忽略大小写统计；超额邀请直接忽略，不驱逐已经展示的邀请。过期记录在新邀请到达和接受/拒绝查询时清理，保留原有 tick 清理。期限改用 `System.nanoTime()`，重复包不能续期。

### 待处理邀请 ID 可以重新绑定（授权内容完整性）

原实现 `invitations.put(id, invitation)` 会覆盖相同 ID 对应的玩家、路由名和目标端口。用户依据先前提示执行 accept 时，可能授权后来被替换的本地端口。需要远端能够向客户端发送控制消息且用户接受邀请；此问题不等于远端无交互即可访问任意本地服务。

修复后，待处理 ID 始终保留首次展示的内容；同一玩家的修改和其他玩家的同 ID 消息都不能覆盖。修改邀请内容需使用新的 ID，用户仍可在 accept 命令中主动指定目标端口。过期邀请在命令入口直接拒绝，不依赖恰好先运行 tick。

### 无关或重复撤销消息触发写盘（拒绝服务放大）

原实现对每个 REVOKE 都执行 save，即使发送者不属于该路由、路由不存在或已被撤销。无效控制消息因而可触发客户端线程上的同步文件替换。

修复后仅当合法发送者实际改变授权或待处理的出站邀请状态时保存；无关与重复撤销不写盘。合法撤销仍关闭活跃连接并持久化，原有生命周期回归测试继续执行。

## 验证

- 修复前：邀请覆盖、邀请洪泛、单玩家占满的三项新回归测试均失败；无关撤销和错误玩家撤销的两项测试也均失败。
- 修复后：Fabric `gradle build --no-daemon --max-workers=2` 成功。13 项单元测试、22 项管理器回归测试、3 项 IPv6 优先模式下的 IPv4 验证均通过；失败、错误和跳过均为 0。

- 使用 Java 25、CI 指定的 Gradle 9.5.1，compileOnly API 来自同工作区已验证的 Krypt04Mcg 0.27.4 Fabric 构建。未修改通信格式或核心 API。
